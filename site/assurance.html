Change assurance levels

How much a change certificate vouches for, from CAL 1 to CAL 4. Each level includes the ones below it.

The core promise

A change reaches the target branch only as bytes that stAirCase derived itself and that a recorded decision covers. stAirCase builds the commit from those bytes, and anyone can check this afterwards. No feature may weaken this promise without saying so.

The four levels

LevelWhat it guarantees
CAL 1 AttributedThe change says which agents and models took part (a certificate and an Assisted-by: trailer). Nothing is enforced.
CAL 2 ReviewedEvery byte an agent wrote is covered by a recorded decision, and the commit can be rebuilt from the approved proposals. Proposals may have been captured after the agent made them.
CAL 3 GatedEvery agent action was decided before it ran, in an isolated worktree. No approved command ran outside a sandbox. stAirCase built the commit.
CAL 4 Two-partyCAL 3, and the decisions, or the final review of the whole change, are signed by an identified person who did not start the run.

A CAL is not a SLSA level. CAL 4 resembles two-party review in SLSA's source track, but stAirCase never claims compliance on anyone's behalf.

Honest reporting

A run records the level it actually reached. A lower level is never shown as a higher one. staircase verify prints the level of a commit, and --min-cal fails below the level you name.

Checks (--check) are evidence about the result: they are recorded in the certificate and a failed one makes staircase verify fail, but they do not change the level, which is about how the change was decided.

The level each way in can reach

Way inHighest levelWhy
Governed runs: staircase claude, staircase codex, staircase run CAL 3 Every action was decided before it ran. A run drops to CAL 2 when an approved shell command ran without a sandbox (for example when a company's managed settings exempt Claude Code's commands from its sandbox), or when changes were reviewed only after the agent made them. Files written by a command that ran in the sandbox are decided before they reach the commit, so they keep CAL 3.
Away runs and hosted sessions: --away, staircase host claude As recorded A declared command's file changes are decided like the agent's, so such a change reaches CAL 2. An approved MCP tool call runs outside stAirCase's sandbox, so a change made with one reaches CAL 2. A run delivered by policy keeps the level it computes; its certificate says that no person reviewed the whole change.
Review after: staircase review CAL 2 The files were changed before anyone decided them: every byte that reaches your branch was decided, but nobody governed what the agent did on its own machine.
Seal: staircase seal CAL 2 The staged files were changed before anyone decided them. For CAL 3, run the agent through stAirCase.
Two-person review: staircase sign CAL 4 Only on a CAL 3 change. CAL 4 needs CAL 3 first, so a reviewed or sealed change stays at CAL 2 even when a second person signs it.

What CAL 4 proves, and what not

A CAL 3 change counts as CAL 4 when a trusted reviewer signed it and the reviewer is not the person the run was made for. By default the certificate records the git user.email of the checkout as the requester, and anyone can set that to anything, so two different strings are not proof of two different people.

  • With staircase verify --require-initiator, CAL 4 counts only when the person who started the run signed the request with a trusted key: two different trusted keys were used, one to start the run and one to review it. That is not proof that two humans hold them; back it with branch protection that requires a human approval.
  • Without --require-initiator, and for runs started without a key, read CAL 4 as "a trusted reviewer signed it".

Signing each decision with --sign-approvals is evidence of who decided each change. It is separate from two-person review, which is what reaches CAL 4.

Who may decide

  • A person can always decide.
  • A policy rule, a verifier's result or a validator model can also decide, within the limits of the level. A model's approvals count only when a person reviews the whole change at the end. With delivery by policy (--deliver policy), only rules of your signed policy decide, and the certificate says no person reviewed the whole change.
  • Decision models used as signals (--signal) can only send a change to a person. They never approve or reject anything.
