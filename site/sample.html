Sample demonstration

Sample: everything on this page is a demonstration with a stand-in model. It is not a governed run of your code, it is not a record of anyone's run, and it is no evidence that stAirCase governed a real agent. Example output below is copied from the project's documentation and uses example values.

See the whole flow once, offline, in about a minute: no API key and no network.

Run it yourself

The demo needs Go, git and curl. Nothing is installed globally: it builds the binaries and works in a disposable temporary workspace that is deleted on exit.

git clone https://github.com/b070nd/stAirCase.git
cd stAirCase
./demo/run-demo.sh          # interactive: you approve each proposal yourself
./demo/run-demo.sh --tamper # a command changes an approved file: you decide, it is put back
./demo/run-demo.sh --drift  # the agent works outside its task: the run is stopped

What it does

  1. Builds staircase and creates a product repository with a README, an obsolete notes file and some uncommitted work of the developer's.
  2. Puts the hello blueprint in its own git repository, imports it and binds it to the project: a topology, one case, two stories, each with the paths it may change.
  3. Compiles the case and starts a run with the HTTP approval server. The run works in its own git worktree.
  4. The supervisor hands the work to the coder, who creates GREETING.md, edits README.md and deletes OLD_NOTES.md. Each call waits for your approval and shows exactly what would be applied: press Enter to approve.
  5. Finalize checks the worktree against the approvals and commits exactly the approved bytes. The demo checks that the run branch holds exactly those three changes, and that your checkout (HEAD, branch, index, status, every file) is byte for byte as before.
  6. You accept both stories; the case is completed. The signed audit chain is exported and verified.

The model is a stand-in, on purpose

A tiny OpenAI-compatible gateway plays the two agents deterministically. Everything else is the real product: the agent runtime and its tools, the model client, encrypted workspace secrets, the approval server, the worktree, finalize and the audit chain. That is why the demo shows the mechanics, and why it says nothing about how well a model does real work.

The tamper mode

With --tamper, after its file is approved the coder asks to run a shell command that appends to the file. You approve the command. It runs, and the file it changed comes back to you as its own decision, marked as already changed. The demo rejects it: the file is put back to the bytes you approved, and only those are committed. Approval is bound to content, not to a preview or a command.

The drift mode

With --drift, after its stories' work the coder keeps proposing files outside both stories' scope. Each goes to you marked as drift; the blueprint allows 2 such proposals, so the 3rd halts the run. Example output, from the demo's documentation:

Sample output

Drift: more than 2 proposals reached outside the stories' scope - halting run #1
  ok    run halted (KILLED) and exited 1
  ok    the case does not run again until 'staircase run 1 --ack-drift'
