Team governance

A team keeps its rules and trusted keys in one git repository, reviewed like any other code. Each developer's workspace takes them from there, pinned to an exact commit.

CAL 4 when a trusted reviewer, who is not the person the run was made for, signs a CAL 3 change. About assurance levels.

The governance repository

team-governance/
  policy.json       the rules and limits every run uses (required)
  allowed_signers   the people trusted for two-person review (optional)
  keys/
    alice.pub       each member's workspace signing key (optional)
    bob.pub
  blueprints/       blueprints the team shares (optional)
    hello/
      blueprint.yaml
      prompts/coder.md
staircase governance use git@github.com:acme/team-governance.git
staircase governance status

governance use fetches the repository, checks the policy with the same strict rules a run uses, and installs the files in your workspace at the branch's current commit. If anything is invalid, nothing changes. From then on:

  • runs use the team's rules and limits;
  • staircase verify and staircase report accept certificates signed by any member's key, so a teammate's commits pass your CI check too;
  • staircase verify counts the team's reviewers for CAL 4 without --allowed-signers.

Changes never arrive on their own: governance status shows the pinned commit and warns when the repository has moved on. Review what changed, then run governance use again. Test a policy change with staircase policy test before you merge it.

Two-person review

A reviewer signs the run's certificate with their SSH key after checking the change:

# the reviewer, in the repository, after fetching the notes:
git fetch origin refs/notes/staircase:refs/notes/staircase
staircase sign staircase/run-7 --key ~/.ssh/id_ed25519.pub --as bob@example.com
git push origin refs/notes/staircase

Anyone checking the change then runs:

staircase verify staircase/run-7 --allowed-signers .github/allowed_signers --min-cal 4

A CAL 3 change counts as CAL 4 when a trusted reviewer signed it and the reviewer is not the person the run was made for. The run's requester is by default the git email of the checkout, which anyone can set. Start the run with your SSH key (--sign-approvals ~/.ssh/id_ed25519 --sign-as you@example.com) to sign the request too, and verify with --require-initiator: CAL 4 then means two different trusted keys were used, one to start the run and one to review it. That is not proof that two humans hold them; back it with branch protection that requires a human approval.

What to protect

Whoever can change the governance repository decides the team's rules and whom its members trust. Protect its main branch like production code: required reviews, and signed commits if you use them.

What this is not

  • No single sign-on, roles or authenticated initiators. Who is trusted is whoever holds a listed key. A run records the git email of the checkout it ran in, which anyone can set; nothing ties a run to a signed-in person.
  • Rollout and revocation are not atomic. Each workspace takes a change when its owner runs governance use; until then it keeps the old rules and keys. A CI check reads the bundle from its base branch, so it changes the moment the merge lands.
  • Durability. On macOS, on a laptop that loses power at the wrong moment, the last decision may be lost. Keep the audit exports and the certificates in git for anything that matters.
