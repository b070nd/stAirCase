Review after, and seal

Some agents work where stAirCase cannot decide their steps before they happen: cloud agents that hand you a pull request, and agents that edit your checkout directly. stAirCase can still make sure only the files you approve are committed, and certify that you did.

CAL 2 The files were changed before anyone decided them. About assurance levels.

Review a cloud agent's branch: staircase review

Cloud agents (GitHub's Copilot coding agent, Codex in the cloud and others) work on their own machines and hand you a branch or a pull request.

git fetch origin pull/42/head:pr-42
staircase review pr-42 --by "Copilot coding agent"
  1. stAirCase shows you what is about to be reviewed and asks you to confirm (--yes in scripts).
  2. It creates a separate worktree of your current branch and brings the branch's changes into it one file at a time. It applies the branch's own diff, so newer work on your branch is kept. A file whose change no longer fits your branch is left out and reported.
  3. Each file comes to you (or your rules) to approve or reject. Rejected files are left out.
  4. Exactly the approved files are committed on a new branch, staircase/run-N, with Assisted-by: <who made them> and a signed change certificate.

--allow limits where the changes may go: a file elsewhere comes to you as drift. A panel of validator models can review the files too (--validator, repeated); when they disagree, you decide.

Agents in your own checkout: attach and seal

Cursor, IDE assistants, or any tool stAirCase has no hooks for edit your checkout directly.

staircase attach                      # while the agent works: plain git commit is refused
# ... the agent edits your files ...
git add -p                            # stage what you want to commit
staircase seal -m "Add a health check" --by Cursor
staircase attach --off                # back to normal
  1. staircase seal takes exactly what is staged, as it is now.
  2. Each staged file comes to you (or your rules, guards, validators and signals) to approve or reject.
  3. Your current branch moves to one new commit with the approved files, your message, an Assisted-by: <agent> trailer and a change certificate.

Rejected changes are not committed and not thrown away: they stay in your working files, uncommitted. Edits you did not stage are left alone. If your branch moved while you were deciding, it is not touched, and the certified commit stays on its staircase/run-N branch.

staircase attach installs a pre-commit hook that refuses git commit and shows how to seal. It is not a wall: git commit --no-verify gets through, which is why the CI check is the second line. An existing pre-commit hook of your own is never replaced, and nothing is written into your repository's files: if core.hooksPath points inside the working tree (a .husky folder), attach refuses and names the setting. staircase seal takes --allow like the other commands.

Why CAL 2, and not more

Every byte that reaches your branch was decided, but nobody governed what the agent did on its own machine or in your checkout. A second person can still sign a reviewed change with staircase sign, but CAL 4 needs CAL 3 first, so a reviewed or sealed change stays at CAL 2. For CAL 3, run the agent through stAirCase (staircase claude, staircase codex): see governed runs.
