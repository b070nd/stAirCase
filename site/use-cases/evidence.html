Evidence inspection

Every run keeps a record of what the agents proposed, who decided, what was committed, and what went wrong. Check it yourself, or hand it to someone else.

The certificate shows the level each change reached. About assurance levels.

Verify a commit's certificate

Each run that commits leaves a change certificate about exactly that commit: a small, signed statement of who helped, what was decided and by whom, and the assurance level the change reached. It holds digests only, never code or prompts. It is attached to the commit as a git note (refs/notes/staircase).

staircase verify staircase/run-7
staircase verify staircase/run-7 --min-cal 3     # fail below CAL 3

For a reviewer on another machine, push the notes with the branch; the reviewer fetches them and verifies with your public key, the only file they need:

git fetch origin refs/notes/staircase:refs/notes/staircase
staircase verify <commit> --key signing.pub

Rebuild a commit from its approvals

staircase rebuild staircase/run-7

verify shows who signed what was decided. rebuild shows that what was decided is what is in the commit, byte for byte: it replays the run's ledger (the base commit and every approved proposal, in order) on the base commit, and the tree it produces must be identical to the commit's tree. A commit that holds anything nobody approved fails, even when its certificate is validly signed. staircase verify --rebuild does both.

The ledger holds the approved content, so it stays in your workspace; to let a reviewer rebuild, give them the ledger file.

The audit chain

Each event of a run is stored with a hash of its content and of the event before it. Changing, removing or reordering any event breaks every hash after it. A decision is written to the chain before the agent learns it, and secrets are removed from every event before it is stored. Each reviewer model's verdict, each launch of an agent and a checkout that held changes the run did not have are events on the chain too.

staircase inspect runs --case 1        # runs of case 1 and their status
staircase inspect log 7                # the events of run 7; also checks the chain
staircase replay 7                     # just the decisions, in order, after checking the chain

Export signed evidence, and let someone else verify it

staircase audit export 7
staircase audit verify ~/.staircase-workspace/audit/run-7.checkpoint.json

audit export writes the run's events to a checkpoint file and signs them with the workspace's Ed25519 signing key. Verification needs only two files, and neither is secret: the checkpoint file and your workspace's public signing key. If any character of the evidence was changed, verification fails.

Add an outside witness: Rekor

A signature proves the evidence was not changed after signing, but whoever holds the signing key could create new, different evidence. To prove when the evidence existed, anchor it in Rekor, Sigstore's public, append-only transparency log.

staircase audit anchor 7
staircase verify staircase/run-7 --check-anchor

Anchoring the change certificate sends only the certificate: commit hashes, digests, decision counts and the level. Anchoring the whole record (staircase audit export 7 --anchor) sends every event of the run, including the agents' reasoning, file paths and the proposed changes, to the Rekor service. If the record must not reach a third party at all, use --rekor-url with a Rekor instance you run yourself.

Report across repositories

staircase report ~/src/shop ~/src/billing --since 30.days --key team.pub

For each repository, report shows how many commits were made by people and how many with an agent, how many of those carry a valid certificate at each assurance level, which agents wrote them, and each agent commit whose certificate is missing, invalid or records a failed check. It never fails; --json prints the same for a dashboard or a spreadsheet.

Review attention

A signed approval proves someone clicked approve, not that they read the change. The certificate also records how many decisions people made, their median time, and how many changes of 20 lines or more they approved in under 5 seconds. It is information, not a gate.

When the evidence cannot be written

The commit is made first; the ledger and the signed certificate are written after it. If either cannot be written, the commit is still on its run branch and the run says so plainly: its outcome is delivered_without_evidence, and the audit chain has an evidence_failed event. With --require-evidence the run also exits non-zero, so a script or CI job cannot mistake it for a complete result.
