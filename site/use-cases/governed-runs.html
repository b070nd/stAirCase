Governed CLI runs

Put staircase in front of your agent. Every change the agent wants to make comes to you first, and at the end exactly what you approved is on a new branch, with a certificate you can check.

CAL 3 when every action was decided before it ran. About assurance levels.

Claude Code and Codex, in one command

If Claude Code is installed and logged in, you need no setup at all. In any git repository with at least one commit:

staircase claude "add a /health endpoint that returns 200"   # or: staircase codex "..."
  1. stAirCase creates what it needs (workspace, project, case) and first shows you what is about to happen: the task, where it may change files, how edits and commands are handled, the model and the budget. Type y and press Enter to start (--yes in scripts).
  2. It runs the agent in a separate worktree and shows you every change it wants to make: press y to approve, n to reject with a reason.
  3. At the end, exactly the approved changes are on a new branch, staircase/run-N, and your checkout is untouched.

If the run is interrupted (a crash, a killed terminal), staircase resume N carries on with the same task, and staircase recover N commits exactly what it had approved.

Gemini CLI and OpenCode are there too (staircase gemini, staircase opencode). Governing Claude Code and Codex is marked experimental; Gemini CLI and OpenCode are still experimental. The compatibility table lists the agent versions that have actually been run.

stAirCase's own agents

With a model provider of your choice, describe the team of agents (a topology), the work (a case with stories, each with the paths it may change), compile it into a plan, check it with gates, and run it with staircase run. The first run guide walks through each step.

What an approval means

stAirCase does not trust what the agent says it will do. For every file proposal it computes itself what the file will contain after the change, starting from the commit the run began on. You approve those exact bytes. When the run ends, stAirCase checks that the worktree holds exactly what was approved and commits only that. Anything else (a file nobody approved, a change after the approval, a commit made by the agent) fails the run, and nothing is committed.

Who decides, in order

  1. stAirCase refuses a proposal it cannot apply as shown: a path outside the repository or inside .git, a symlink, text to replace that is not in the file, or a new file larger than 200 KiB.
  2. Drift supervision can stop the run, or send the proposal to a person, for a change outside the stories' scope, too many files, or a checkpoint.
  3. Guards send a change to a person, whatever the rules say, when it adds something risky: a file that is not text, hidden Unicode characters, a file made executable, a change to dependencies, or what looks like a secret.
  4. Where your checks are defined, and sensitive paths. A change to the script a check runs, the tests it is given, or a path you name with --protect goes to a person, whatever the rules say. So does a change to a CI or build file, a dependency file, an .env file, a shell script or a CODEOWNERS file.
  5. Your policy rules (policy.json) can approve or reject it automatically, also by the files and size of the change (paths, max_lines, max_files, new_files_only, no_deletions).
  6. The agreed task, with --approve-in-scope, approves in-scope file changes that are not sensitive; with --approve-on-evidence it approves them only when the evidence is there.
  7. A validator model or a panel of them, if you turned one on, can decide in-scope file changes. Each model's verdict is written to the audit chain before the decision.
  8. A person decides everything else.

Shell commands always go to a person. Each decision is written to the audit chain before the agent learns it. If the record cannot be written, the proposal is rejected and the run stops.

Ways to decide as a person

WayHow
In the terminal (default)y approves; n (or q, Esc) rejects: type a reason and press Enter. The agent receives your reason and can try again.
In your browser--approval-port 8765 serves a review page on this machine only and prints its link.
One page for every sessionstaircase serve shows the waiting proposals of every session on this machine on one page.
From a scriptthe approval API on 127.0.0.1, with a bearer token.
From a servicea webhook, signed with a shared secret (HMAC-SHA256).

With --sign-approvals ~/.ssh/id_ed25519, each decision you make carries your SSH signature, so who decided is provable. With --require-signed-approvals, a decision that is unsigned or not from a trusted signer is refused.

Approve the task, on evidence

staircase claude "add a /health endpoint" --allow "src/**" --approve-on-evidence \
  --check "go vet ./..." --check "go test ./..."

A change inside the scope (not a sensitive file, not flagged by a guard, not stopped by a limit) is approved only when every --check passes, run in the sandbox on the exact state the change would produce, and the --validator models, if you named any, agree. Otherwise the change comes to you with what was missing. You still see anything outside the scope, sensitive files, guard hits and shell commands, and you approve the whole change once at the end.

The evidence is as good as your checks: with weak tests, evidence-based approval is weak approval. A check reads the files the agent changes, so an agent that may edit a test (or the script a check runs) can make the check pass. The paths where your checks are defined are protected: a change to one always goes to a person (--protect adds more).

Shell commands

Shell commands are off by default: agents can only ask to run commands when you allow it, and a person approves each one. Approved commands and checks run in an OS sandbox with no network, writes only in the worktree, and no access to your credentials or stAirCase's keys. --sandbox required refuses to run without one.

A client's repository: the project profile

When the repository is a client's, nothing of stAirCase should go into it. A project's profile keeps what is true of it for every run in your workspace instead: the paths that always need a person, the scope a change may touch, the checks and the sandbox, ignored directories that checks need (such as vendor/, shown read-only), instructions that every agent is told before its task, and files the agent must not read (a tracked auth.json). The built-in agent and Claude Code enforce the last one; Codex, Gemini CLI and OpenCode cannot, so a run with them on such a project is refused. A project's profile. For a change that spans several repositories, a change set ties the runs under one id and verifies them together.

Limits

  • The agent program itself runs as your user. For stronger isolation, run stAirCase in a container or VM.
  • What the agent reads, and what the model provider receives, is not confined, except for the files you name in the project profile: a run sends code to your model provider.
  • A run drops to CAL 2 when an approved shell command ran without a sandbox.
