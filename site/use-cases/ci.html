CI verification

A CI check can refuse pull requests with a change that is not properly certified, and require a minimum assurance level.

The check requires a level; it does not raise one. About assurance levels.

Set up the check

Commit your workspace's public key to the repository's protected branch (it is public; copy ~/.staircase-workspace/.signing.pub, for example to .github/staircase.pub), and add a workflow:

name: stAirCase
on: pull_request
permissions:
  contents: read
  attestations: read
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0
      - uses: b070nd/stAirCase@v1.1.0
        with:
          version: v1.1.0                            # the verifier that runs, pinned
          key: .github/staircase.pub
          all: true                                  # every commit needs a certificate (the default)
          allowed-signers: .github/allowed_signers   # optional: trusted reviewers, for CAL 4
          min-cal: 3
          rebuild: true                              # also replay each commit from its ledger

Push the certificates together with the branch:

git push origin staircase/run-7 refs/notes/staircase refs/notes/staircase-ledger

The same check runs locally:

staircase verify main..HEAD --all --min-cal 3

Which verifier runs

The check installs the release of staircase named by the version input, or the release tag the action is used at, after verifying how it was built: the build attestation must come from the repository's release workflow for that exact tag, and a binary that was not verified is never run. When the action is used at a ref that is not a release tag and no version is set, the latest release is installed and the step warns that the verifier is not pinned. For a reproducible check, pin the verifier.

Where the trust comes from

The key and the allowed signers are read from the pull request's base branch (or trust-ref), never from the pull request's own files: a pull request that replaced the key would otherwise vouch for itself. Outside a pull request, set range and trust-ref to a protected branch or tag; without trust-ref the check refuses to run.

Protect the key and signers paths with CODEOWNERS and a ruleset that requires review, and make this check a required status check. A check that can be skipped or edited by the change it judges is not a gate.

If your bases differ in what they require (another trusted key, another min-cal), give each its own check name and require only that base's name in that base's ruleset. GitHub attaches a check run to a commit, so with one shared name a pull request that passes into a laxer base unlocks the same commit for a stricter one.

Every commit, and rebuild

  • By default every commit of the pull request needs a certificate. all: false checks only commits that name an agent in an Assisted-by: trailer, which is advisory: a commit an agent made without the trailer looks like a person's.
  • With rebuild: true, each commit is also replayed from its ledger and must have exactly the tree the ledger produces: a validly signed certificate on a commit that holds other bytes fails. A commit with no ledger fails.
  • A failed check recorded in a certificate makes staircase verify fail, so a CI check that requires certificates also requires passing checks.

Limits, stated plainly

  • A certificate is about one commit id. Squash-merge and rebase-merge make new commits that carry no certificate: check the pull request's own commits before merging, and merge with a merge commit, or certify the merged result with staircase seal.
  • A pull request from a fork has no notes in your repository and fails closed.
  • Notes are ordinary refs: anyone who can push to them can overwrite a note, so restrict who may push refs/notes/staircase*.
  • A pull request that edits the check's own workflow runs its own version of it under on: pull_request: protect .github/ with required review, or run the check on pull_request_target.
  • None of this has been exercised against a real organization ruleset; do that once with a test repository before relying on it (demo/ruleset-fixture.sh builds one).
