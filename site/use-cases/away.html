Working while you are away

Start a task, leave, and come back to one decision. Nothing is committed before you accept it.

The certificate records the level a run reached; a change made with a declared command or an approved MCP tool call reaches CAL 2. About assurance levels.

staircase claude "add a /health endpoint with a test" --allow "src/**" --away --check "go test ./..."
# ... later
staircase decide

While you are away

  • Approved on evidence only. A change inside --allow is approved when every --check passes on the exact state it would produce. Your policy rules still apply. --away needs at least one --check.
  • What needs you is parked, not asked. A change without evidence, one outside the scope, a sensitive file, a guard hit, a change to where your checks are defined or a shell command would come to you; while you are away it is parked. The agent is told at once that it is kept for you, and to go on with what it can do without it. The parked proposal is on the audit chain with why it needed you. It is never applied by itself.
  • The end is checked, not announced. When the agent stops, your checks run once more on the whole approved change. A change that does not pass ends the run failed. One that passes ends it awaiting review, with nothing committed. The process exits; nothing has to keep running.
  • Delivery by policy. With --deliver policy, rules of your signed policy can deliver a change to the run branch without your review, but only when seven conditions hold, all read from the run's verified history. If one fails, the run waits for you and staircase decide names it. Review stays the default.

Evidence is as good as your checks. A check reads the files the agent changes, so an agent that may edit a test (or the script a check runs) can make the check pass. The paths where your checks are defined are protected: a change to one always goes to a person, so while you are away it is parked (--protect adds more).

When you are back: staircase decide

KeyWhat happens
Y or IAccept: exactly the change on offer is committed on staircase/run-N with its certificate. The agent is not started again.
N or OReject: nothing is committed.
DDefer: nothing is decided, the run keeps waiting.
ZClarify: Claude Code starts in plan mode (read-only) in a separate directory that holds only this change, its evidence and what was parked. Nothing said there decides anything.
PPrototype a parked change in a checkout that is thrown away. One that passes your checks can be adopted into the change as your approval; you then decide on the new review.

Without a terminal: staircase decide 12 --accept or --reject, with -m for why. A decision is bound to the review you saw.

How each run stands

Every run has one outcome, read from its verified audit chain alone: running, awaiting review, blocked or partial, failed, no change, delivered, or delivered with incomplete evidence. staircase decide shows it with the run's attempts, time, tokens and cost against its limits. If the agent was lost (its process was killed), the run is parked until you say you looked with staircase acknowledge <run>; that launches nothing.

Declared commands and tools

An away run parks every command, because a command needs a person. A command you can name in advance can be declared:

staircase claude "regenerate the API client and fix what breaks" --allow "src/**" --away --check "go test ./..." \
  --allow-shell-exec --away-command "go generate ./..." --sandbox docker:image=golang:1.26-bookworm

A declared command runs without asking only if it is exactly what you wrote, in the worktree's root, and only in a sandbox without network; anything else is parked as before. It is recorded as your decision made in advance, and the files it changes are decided like the agent's (on evidence, or parked), so such a change reaches CAL 2. Gemini CLI and OpenCode run their commands without a sandbox, so they cannot be given declared commands.

An MCP server's tool call is decided like a command: never by a policy rule, and while away it is parked unless you declared that exact tool (--away-tool mcp__<server>__<tool>). An approved tool call runs outside stAirCase's sandbox, so a change made with one reaches CAL 2.

Sessions another program starts

Some tools start Claude Code for you: a runner such as Cloudroom keeps agents working in its own sessions, with Claude Code's approvals switched off. Name staircase host claude as the runner's Claude Code program, and each session it starts is an away run: nobody is asked, a change is approved only when your checks pass on it, anything that needs you is parked, and the change waits for staircase decide.

cd your-repository
staircase host setup --allow "src/**" --check "go test ./..." --pass-env CLAUDE_CODE_OAUTH_TOKEN
  • The runner's stdin and stdout reach Claude Code untouched; stAirCase's own output goes to a log in the workspace.
  • Every call of the runner's MCP tools is a proposal stAirCase decides; a change made with an approved tool call reaches CAL 2.
  • An argument stAirCase does not know is refused, naming it, because it could widen what the agent may do.
  • A runner can resume a session it started (--resume): an interrupted run continues, and one that awaits review is reviewed again as a whole.
  • The agent works in stAirCase's run worktree; what reaches staircase/run-N is only what stAirCase derived from recorded decisions, with its certificate.

What it guarantees, and what not yet

  • The commit holds exactly the files the chain says were approved, derived again from the base commit, and the tree must be the one whose checks passed.
  • The certificate cites the checks that ran on that tree and says the change was made while you were away and accepted afterwards.
  • Not yet: a run that requires signed decisions cannot be away; a forked runner session (refused, naming the reason); hosted sessions of other agents than Claude Code.
