# stAirCase v1.0.0 - governed changes, verifiable evidence (draft text; the published notes are the CHANGELOG section)

> Working copy. It is not a GitHub release and creates nothing. Every sentence states only what
> [the readiness record](v1.0.0-readiness.md) marks *met* or *accepted*. Before it is used: add the release gate's result after the tag, and
> update the Action line if the ruleset run was done. The GitHub release body itself is cut from the CHANGELOG by `packaging/release-notes.sh 1.0.0`.

stAirCase governs AI-assisted Git changes and produces independently verifiable evidence of the approved content: only bytes
derived by stAirCase and covered by a recorded decision reach the branch.

## What changed since v0.11.0

- **Continue what was interrupted.** `staircase resume <run>` continues a run that was killed before it committed, under the
  policy, plan and options it saved when it started, from the state its audit chain says it stood in. Work the agent did after
  its last approval is never adopted. For Claude Code, Gemini CLI and Codex the vendor's own session is resumed (its id is on the
  chain); when that cannot be done it refuses, and `--fresh-context` continues in a new session grounded by the chain.
- **Runs, sessions and the coordinator are owned.** A live run cannot be recovered; a dead one is recovered without `--force`.
  One `staircase serve` per workspace; a dead session's proposals decide nothing.
- **Recovery is stricter and more complete**: an exact journal-cut classifier, a large approved change is recoverable, a request
  that cannot be recorded is refused, an approval is consumed at its decision on the chain.
- **A decision model's invalid answer can no longer read as reassuring**: it sends the change to a person.
- **A required admission check for your own repository**: a fixture, an importable ruleset and readers that keep the evidence of
  a run under a ruleset (see [testing](../testing.md)).

## Verification and rebuild

`staircase verify` checks a commit's signed change certificate with only the public key; `verify --rebuild` also replays the
commit from its ledger and requires the same tree. Retained evidence for the candidate commit: [v1.0.0 candidate](../release-evidence/v1.0.0-candidate.md) (CI, CodeQL and
Scorecard green, Linux and macOS evidence passed on a clean tree); the release gate's result is added after the tag.

## Compatibility and upgrade notes

From 1.0 the six contracts (certificate, hook bridge, records, decision-model interface, verifier results, policy file) follow
semantic versioning ([contracts](../contracts.md), [compatibility](../compatibility.md)). Real runs of releases from v0.3.0 on
are verified and read by today's program (`tests/historical.bats`). A run begun by an older version cannot be continued, only
recovered. The earlier Bash implementation of `staircase` had its own 1.0.0 to 1.2.0 (kept at the bottom of the CHANGELOG as `[bash 1.x.0]`); this
1.0.0 is the Go program's first, and the Homebrew formula's `version_scheme 1` orders it after them.

## Installation

Signed release archives with a build attestation; check a release without signing in to GitHub with `packaging/verify-release.sh`.
Homebrew: `brew install b070nd/staircase/staircase`; or `go install github.com/b070nd/stAirCase/src/cmd/staircase@v1.0.0`; or the archive for
your platform, whose checksum, signature and build attestation `packaging/verify-release.sh v1.0.0` checks.

## The verify Action

Pin the Action and the verifier, trust the protected base, check every commit and rebuild:

```yaml
- uses: b070nd/stAirCase@v1.0.0
  with: { version: v1.0.0, key: .github/staircase.pub, all: "true", rebuild: "true", min-cal: "2" }
```

This is the recommended example; the Marketplace listing is a later step. As of this draft the Action under a required check that
blocks a merge has not been run in GitHub (update this line if the ruleset run is done first).

## Known limitations

- A change certificate is about one commit id: squash or rebase merges make commits that carry none (see [audit](../audit.md)).
- An approval being consumed in the instant a deadline passes counts, and is recovered once (accepted, [approvals](../approvals.md)).
- A run killed by v0.8.0 after its commit is recovered by a manual procedure ([safety](../safety.md)).
- Decision models (`--signal`) can only send a change to a person, and are **not a safeguard as configured**: on 24 synthetic changes a local Laya 0.4.0 missed 11 and 9 of 12 risky ones at the 0.5 threshold ([results](../evaluation/README.md)); Jev through the gateway is not measured (by decision), so no accuracy is claimed for it.
- The independent implementations of the specification are the maintainer's own scripts.
- Windows is experimental and untested; its run locks exclude nothing.
