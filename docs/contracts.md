# The six contracts, audited

[Compatibility](compatibility.md) names six interfaces that other tools build on. This page is the audit
behind that promise: for each, what it is in the code today, how it changed across the releases, what pins it
(tests, independent vectors, fixtures made by old releases) and what is not yet promised. It describes what was
checked, at the v0.11.0 line; it does not widen the promise.

**Supported versions.** Today's `staircase` verifies, rebuilds and reads the evidence of every release from
**v0.3.0** to the current one, checked against a real governed run made by each of v0.3.0, v0.4.0, v0.5.0, v0.6.0,
v0.7.1, v0.8.0 and v0.10.0 (`docs/spec/historical`, `tests/historical.bats`). Releases without a fixture (v0.2.0,
v0.7.0, v0.9.0, v0.11.0) are covered only by the neighbouring ones: v0.2.0 predates the change certificate, and the
others differ from a checked release by changes listed below. A release before v0.3.0, and the Bash-era 1.x versions
(a different product line, the CHANGELOG's bottom), are not supported.

**What the check does not show.** One run per release, made with a stand-in agent on one small task: it shows that
the contracts' formats are read, not that every feature of every release round-trips. A fixture was made once and is
kept; the tests do not regenerate it, so they stay about the old releases.

## 1. The change certificate

- **What:** an in-toto Statement v1 in a DSSE envelope, predicate type `docs/adr/0002-change-certificate.md#v1`,
  signed with the workspace's Ed25519 key, kept as a git note (`refs/notes/staircase`); specified in
  [certificate-v1](spec/certificate-v1.md).
- **History of the predicate** (the keys of the certificate each release wrote, read from the fixtures):

  | Release | Keys of `predicate` |
  |---|---|
  | v0.3.0 | `run`, `baseCommit`, `planDigest`, `agents`, `decisions`, `chainHead`, `cal` |
  | v0.4.0 and v0.5.0 | the same, and `requestedBy` |
  | v0.6.0 on | the same, and `ledger` (the digest of the ledger the commit rebuilds from) and `policy` (the digest of the policy it decided under) |
  | optional, when a run has them | `blueprint`, `notes`, `initiator`, `checks`, `signed`, `attention` |

  The predicate type stayed `#v1` throughout: every addition is an optional field, and verifiers ignore unknown
  fields, as the compatibility page promises.
- **Pinned by:** 13 independent vectors (`verify_vectors.py`, written from the specification alone), `TestVerify_*`,
  the historical fixtures, `TestContract_every_certificate_field_is_in_the_specification` (a field in the code that
  the specification does not describe fails the build).
- **Not promised:** the segment count of a continued run is deliberately not in the certificate
  ([ADR 0005](adr/0005-durable-continuation.md)); any change of meaning needs `#v2`, with `#v1` still accepted.

## 2. The hook bridge

- **What:** `staircase hook <agent> [--governed | --require]`: the agent's hook JSON on stdin, the answer on stdout,
  exit 2 blocks, the session found through `STAIRCASE_HOOK_FILE` or `--file`
  ([ADR 0003](adr/0003-hook-bridge.md)). Registered events: Claude Code and Codex `SessionStart`, `PreToolUse`,
  `PostToolUse`, `Stop`; Gemini CLI `SessionStart`, `BeforeTool`, `AfterTool`; OpenCode through its plugin.
- **History:** the command text stayed `staircase hook <agent> --governed`; v0.8.0 appended `|| exit 2` (a host that
  carries on after any other failure would let the tool through) and made every unreadable call and every answer that
  is not a decision a block; v0.10.0 registers `SessionStart` for Claude Code and refuses a session whose hooks never
  ran (as the other agents already did); v0.11.0 starts Gemini with `--skip-trust`.
- **Pinned by:** `TestRunHook_*` (reply checks, every failure blocks), the stand-in agents, the synthetic Claude Code
  host, `TestContract_every_hook_event_is_documented`. Real runs of Claude Code 2.1.236, Gemini CLI 0.46.0 and Codex
  exercised a file write ([compatibility](compatibility.md)).
- **Not promised:** that a host runs a hook at all, and what a host does when a hook is slow (it may run the tool; the
  end-of-run check is what holds). Settings managed by a company are generated by `staircase hook-template` and must be
  generated again when the command text changes (v0.8.0).

## 3. Proposal and decision records (the audit chain)

- **What:** the run's events, each SHA-256 chained to the one before it, and the signed checkpoint `staircase audit
  export` writes ([audit evidence](audit.md)).
- **History:** chain **version 1** (v0.3.0 to v0.6.0) hashed payload, previous hash and commit; **version 2** (v0.7.0
  on) also covers the event type ([ADR 0004](adr/0004-audit-chain-version-2.md)). A chain may mix versions, an entry
  cannot be passed off as another version, and every version stays verifiable. Events added: `policy_snapshot` (v0.8.0),
  `commit_prepared` (v0.9.0), `unconsumed` marks on decisions, `run_recovered` and friends; no event changed meaning.
  Writing order changed in v0.6.0 (every approval is journaled before it is answered).
- **Pinned by:** 6 independent chain vectors (`audit_chain_vectors.py`), `TestChain_*`, every checkpoint in the
  historical fixtures (version 1 and 2), `TestContract_every_audit_event_is_documented` (an event the code writes that
  [audit](audit.md) does not list fails the build; this audit found nine undocumented events and the page now lists
  them).
- **Not promised:** version 1 cannot be strengthened afterwards (G-2): an event of a run written before version 2 can
  be relabelled without the chain noticing.

## 4. The decision-model interface

- **What:** typed questions (`boolean`, `choice`, `score`) about a change, answered with probabilities, through the
  gateway's `POST /v1/evaluate` or a TypeSafe-compatible `/v1/systemone` (`--signal`, `--signal-url`), now written
  out as a contract in [approvals](approvals.md#a-decision-model-as-a-signal): request, answer, the three questions
  asked, the 0.5 threshold, the limits (1 MiB, 30 s).
- **History:** introduced in v0.4.0; the questions and the rule that a model can only send a change to a person have
  not changed; an answer that is not what was asked (a missing or out-of-range probability, a choice that was not offered) is now an error
  and sends the change to a person, where a missing probability used to read as 0. Measured on 24 synthetic changes (2026-10-07), Laya missed most risky ones at the 0.5 threshold; Jev is not measured, by decision ([docs/evaluation](evaluation/README.md)).
- **Pinned by:** `TestSignal_only_sends_changes_to_a_person`, `TestSignal_url_talks_to_a_local_server`,
  `TestClient_Evaluate`, `TestClient_an_invalid_answer_is_an_error_never_a_safe_one`,
  `TestSignal_a_wrong_late_or_invalid_answer_only_sends_the_change_to_a_person`, `TestContract_the_decision_model_interface_is_documented`.
- **Not promised:** the threshold is fixed at 0.5 and not calibrated; a server that answers differently from the
  documented shape is an error, which sends the change to a person.

## 5. Verifier results

- **What:** `checks` in the certificate (`--check`): the command, `exitCode` (-1: could not run), `sandboxed`,
  `outputSha256`; `verify` fails a failed check. `check_ran` records each run on the chain.
- **History:** unchanged since introduced; `check_ran` was added to the documentation in this audit (it had been written
  since v0.4.0).
- **Pinned by:** the specification and its vectors (`05-failed-check`), `TestVerify_fails_a_failed_check`,
  `TestRun_says_what_evidence_the_commit_has`.
- **Not promised:** linking full test reports as in-toto test-result attestations is planned as an addition.

## 6. The policy file

- **What:** `policy.json`: `version`, `rules` (action types, confidence, extensions, agent names, effect) and `limits`
  (`max_auto_approved`, `max_total_yields`, the drift limits), plus `allow_blanket_deny` ([approvals](approvals.md)).
- **History:** strict since v0.2.0 (an unparsable file, an unknown field or a blanket deny stops the run); from v0.6.0
  the file is read once and a run decides under that read (v0.8.0 records its digest as `policy_snapshot`).
- **Pinned by:** `TestLoadEngine_*`, `TestEvaluate_*`, `TestPolicyScenarios_command` and the scenario tests,
  `TestContract_every_policy_field_is_documented` (a field of the file that the documentation does not describe fails
  the build).
- **Not promised:** a continued run keeps the policy it started under; a changed policy applies to new runs only
  ([ADR 0005](adr/0005-durable-continuation.md)).

## Open at 1.0

| Item | Status |
|---|---|
| Independent implementations are the maintainer's own scripts | open: a second implementation by someone else would be stronger evidence (external) |
| A fixture of a release made with a real agent, not a stand-in | open: the fixtures are stand-in runs |
| Fixtures for v0.2.0, v0.7.0, v0.9.0, v0.11.0 | open: the neighbouring releases cover them; they can be added with `docs/spec/historical/generate.sh` |
| Audit chain version 1 weakness | stated limit (G-2), not fixable afterwards |
| The in-toto predicate proposal | drafted ([in-toto-predicate](spec/in-toto-predicate.md)), not submitted: it needs a person to send it |
| Versioning at 1.0 | from v1.0.0 the six follow semantic versioning ([compatibility](compatibility.md)); the 1.x numbers of the Bash line (the CHANGELOG's bottom) are a different product, and the Homebrew formula's `version_scheme` already orders the Go releases after them |
